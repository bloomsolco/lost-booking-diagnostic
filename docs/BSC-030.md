# BSC-030: Keep each paid diagnostic for at least 90 days

Approved by DEC-020. Built by Ray. **Candidate only.** It is not merged, not deployed and not applied to any database.
Branch: `bsc-030-report-retention`. Vercel deployments are switched off for this branch in `vercel.json`.

## What it does, in plain English

- **One purchase gets one record.** When a buyer submits, the server checks the license with Gumroad (as it does today). Before it fetches any page or calls the model, it reserves a record for that purchase. The record holds the buyer's answers.
- **The report is saved into the same record.** Answers and report sit side by side in one database row, written in one transaction. The database refuses a finished record that is missing either one.
- **The buyer gets the same report every time.** The first response is built from the stored copy, and so is every later retrieval. Both are byte-identical. If the buyer submits the form again, they get their stored report back. The model is not called again. (The review screen already tells buyers "This runs once"; the server now enforces it.)
- **Only the license key opens it.** The raw key is never stored. Records are found by a one-way hash of the key. There is no list, search or browse function anywhere, and the public database roles are locked out. The admin tool can extend or delete a record but cannot read one.
- **Failures end cleanly.** Each purchase gets at most 3 generation attempts. Attempts 1–2 end in `failed`, and the buyer can try again. Attempt 3 ends in `failed_final`, and the buyer is told to reply to their receipt. An attempt that goes silent for 5 minutes (for example, a crashed function) is closed out and counts as one attempt.
- **Retention is stored on each record.** Each record carries its own `retain_until` date, set to 90 days at creation. The database refuses anything shorter. Staff can extend it but never shorten it. Buyers can delete their own copy from the report screen, and staff can delete any record. A daily job wipes expired records. Deleting clears the answers and the report. A small stub (key hash, product, dates) remains so the purchase can't quietly regenerate and the log still makes sense.
- **Everything is logged.** Every claim, save, failure, retrieval (including failed lookups), deletion, extension and purge writes a log row. The log row is written in the same database transaction as the action, so an action can't happen without its log entry. The log can't be edited or deleted, and it never contains answers, report text or license keys.

## Tests and results

```
cd tests && npm install
node --import ./dns-stub.mjs local-harness.mjs     # 68 passed, 0 failed  (existing checks)
node --import ./dns-stub.mjs retention.test.mjs    # 64 passed, 0 failed  (BSC-030)
```

- `dns-stub.mjs` is needed only where DNS is unavailable, such as the build sandbox. It resolves only `example.com/.net/.org`. Without it, untouched `main` fails the same 16 source-fetch checks, so those failures come from the sandbox, not from this change. With it, `main` also passes 68/68.
- The fake Supabase runs the migration file **unmodified** on real Postgres 17 (PGlite). Constraints, grants, row-level security and the append-only trigger are therefore tested for real. The `service_role` is set up with BYPASSRLS, as it is in Supabase.
- Two bugs were found and fixed during testing. Postgres `jsonb` re-orders keys, which (1) broke the stored field order and (2) made the first response differ from later retrievals byte-for-byte. Fix: every response is now built from the stored copy, with fields in a fixed order.

## What could go wrong and how it's handled

| Risk | Handling |
|---|---|
| Database down when a buyer submits | Refused with 503 **before** any model spend or page fetch. Nothing is half-written, and the license isn't used. (R5h) |
| Database down after the report is generated | 4 save attempts are made (1 + 3 retries), then the buyer still sees the report, plus a "save the PDF now, no copy was kept" warning. The record is marked `failed` / `storage_write_failed`, so it isn't left in limbo. (R5j–l) |
| Save succeeded but the reply was lost | Retried. The database recognises the identical save and doesn't write twice. (R5i) |
| Function crashes mid-generation | The record stays `pending`. After 5 minutes the next attempt closes it out, logs it and counts it. (R5f–g) |
| Double-click or two tabs | The second request gets 409 "already being generated". The database lock means only one attempt runs. (R5e) |
| Someone guesses keys | Keys are long random Gumroad strings, and each guess must also pass Gumroad's check. Failed lookups are logged. No rate limit was added (see Open questions). |
| Stolen license key | Whoever holds the key can read or delete that one report. This is the same trust model as generation today. |
| Refunded buyer | Can't generate or retrieve, but **can** delete their data. (R6o) |
| A database change breaks the format | A format tag is checked on write (by the database) and on read (by the server). A mismatched record returns an error and is never shown half-rendered. |
| Retention set too short by mistake | `REPORT_RETENTION_DAYS` below 90 is raised to 90, and the database rejects it anyway. (R6b–c) |
| Purge job doesn't run | Expired reports are refused at read time regardless (R6k). The job catches up on its next run. |
| Branch preview exposes unfinished endpoints | Vercel deployments are off for this branch. |

## Privacy-policy wording changes needed

The policy page isn't in this repo, so these changes are written against its described position ("inputs are not stored"). **The founder, or a lawyer, must approve the final text.** These are factual descriptions of what the system does. They are not legal claims, and I have not judged compliance with any law.

1. **Replace** any sentence saying intake answers/inputs are not stored **with:** "When you run the Lost Booking Diagnostic, we keep your intake answers (name, email, business details, the public links you provide, and your answers about your business) together with the report generated from them."
2. **Add (purpose):** "We keep them so you can open the same report again using your license key, and so we can help if something goes wrong with your report."
3. **Add (how long):** "We keep each diagnostic for at least 90 days from when you submit it. We may keep a diagnostic longer if you ask us to or if we need it to resolve a support request. Once its storage period ends, your answers and report are deleted automatically."
4. **Add (access):** "Your stored report can be opened only with the license key from your Gumroad receipt. Keep that key private: anyone who has it can open or delete the report."
5. **Add (deletion):** "You can delete your stored answers and report at any time from the report screen, or by replying to your receipt email. After deletion, the report can't be retrieved or generated again with that license key. We keep a minimal record that a diagnostic existed for that purchase (not your answers or report) and a log of when it was created, opened and deleted."
6. **Add (what isn't stored):** "We don't store your license key itself, only a one-way code derived from it."
7. **Add (processor):** the hosting/database provider that holds this data (Supabase) needs listing wherever the policy lists service providers. *Founder to confirm how the policy currently names vendors.*
8. **Check** for any "we don't retain", "nothing is saved" or "processed only in your browser" lines elsewhere (Gumroad product page, receipt copy, the access-guide PDF, bloomsol.co FAQ) and align them.

In-tool copy already changed on this branch (founder to approve with the policy): the email hint now says *"A copy of your answers and your report is kept for at least 90 days so you can open it again with your license key."* The footer adds *"Retrievable with your license key"*.
